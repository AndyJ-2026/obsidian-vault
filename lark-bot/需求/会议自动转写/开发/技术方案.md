# 技术方案

## 现有架构

```
bot.py（单文件，~620行）
  ├─ 事件轮询：watch_event_dir() → process_event()
  ├─ AI 处理：call_ai() + parse_ai() → JSON {reply, action, params}
  ├─ 动作执行：execute_action() 分发到 do_meeting/do_cancel/do_search/do_digest/do_remind
  ├─ 消息发送：lark_cmd() 封装 lark-cli 调用
  └─ 定时任务：scheduler() 线程（20:00 日报 + 提醒检查）

meeting-cli（独立项目）
  ├─ audio_capture（Swift 二进制）→ PCM 16kHz mono stdout
  ├─ transcribe.py → FunASR Paraformer-large 实时转写
  └─ meeting.sh → 入口脚本，串联录音→转写→纪要→Obsidian
```

## 改动方案

### 核心思路
- bot.py 新增 `transcribe` action，处理录音生命周期（开始/停止）
- 录音复用 meeting-cli 的 `audio_capture` 二进制（不重写）
- 转写引擎从 Paraformer-large 换成 Qwen3-ASR 1.7B（新写转写脚本）
- 纪要生成、文档创建、消息发送全在 bot.py 内完成

### 新增文件

```
lark-bot/
├─ bot.py                    ← 修改：新增 transcribe action
├─ transcribe_qwen.py        ← 新增：Qwen3-ASR 离线转写脚本
└─ requirements.txt          ← 修改：加 transformers/qwen 依赖
```

### bot.py 改动细节

#### 1. Prompt 修改
REPLY_PROMPT 和 CHAT_PROMPT 的 action 列表新增：
```
- transcribe_start: 开始会议转写 → params: {}
- transcribe_stop: 停止转写并生成纪要 → params: {}
```

#### 2. 新增全局状态
```python
# 转写会话状态
_transcribe_state = {
    "active": False,        # 是否正在录音
    "pid": None,            # audio_capture 进程 PID
    "audio_file": None,     # 临时音频文件路径
    "start_time": None,     # 开始时间
}
```

#### 3. 新增函数

**do_transcribe_start(chat_id)**
1. 检查是否已在录音（同一时间只允许一个）
2. 生成临时文件路径：`/tmp/meeting-cli/bot_<timestamp>.pcm`
3. 启动 audio_capture 子进程，输出重定向到临时文件
   ```python
   proc = subprocess.Popen(
       [AUDIO_CAPTURE_BIN, "--system-only", "--app", "Lark"],
       stdout=open(audio_file, "wb"),
       stderr=subprocess.DEVNULL
   )
   ```
4. 更新 `_transcribe_state`
5. 回复用户："开始录音了，会议结束后跟我说一声~"

**do_transcribe_stop(chat_id)**
1. 终止 audio_capture 进程
2. 回复用户："录音结束，正在转写..."
3. **在新线程中执行**后续流程（避免阻塞事件处理）：
   a. 调用 `transcribe_qwen.py` 转写音频文件 → 得到文本
   b. 调用 AI 生成结构化纪要（Markdown 格式）
   c. 保存到 Obsidian `会议纪要/` 目录
   d. `lark-cli docs +create --markdown <file>` 创建飞书云文档，拿到 URL
   e. `lark-cli im +messages-send --user-id <jake> --markdown "..."` 发送：
      - 会议主题概括
      - 云文档链接
   f. 删除临时音频文件

#### 4. execute_action 新增分支
```python
elif action == "transcribe_start":
    return do_transcribe_start(chat_id)
elif action == "transcribe_stop":
    return do_transcribe_stop(chat_id)
```

### transcribe_qwen.py

独立脚本，接收音频文件路径，输出转写文本：
```bash
python3 transcribe_qwen.py --input /tmp/bot_xxx.pcm --output /tmp/bot_xxx.txt
```

- 模型：Qwen3-ASR 1.7B（transformers + torch）
- 输入：PCM 16kHz 16-bit mono（与 audio_capture 输出一致）
- 输出：带时间戳的文本文件
- 离线处理，不需要实时

### audio_capture 复用

直接使用 meeting-cli 的编译好的二进制：
```python
AUDIO_CAPTURE_BIN = os.environ.get(
    "AUDIO_CAPTURE_BIN",
    os.path.expanduser("~/meeting-cli/audio_capture")
)
```

不复制不重写，通过环境变量指定路径。

## 数据流

```
用户私聊 "帮我转写"
  → process_event() → AI 识别 action=transcribe_start
  → do_transcribe_start()
      → subprocess: audio_capture --system-only --app Lark > /tmp/bot_xxx.pcm
      → 回复 "开始录音了"

用户私聊 "结束"
  → process_event() → AI 识别 action=transcribe_stop
  → do_transcribe_stop()
      → kill audio_capture
      → 回复 "录音结束，正在转写..."
      → 新线程:
          → transcribe_qwen.py → 转写文本
          → AI 生成纪要 Markdown
          → 写入 Obsidian 会议纪要/
          → lark-cli docs +create → 飞书云文档 URL
          → lark-cli im +messages-send → 私聊发送概括+链接
          → 清理临时文件
```

## 风险与注意事项

1. **audio_capture 需要麦克风/屏幕录制权限** — 首次运行需在系统设置中授权
2. **Qwen3-ASR 首次运行需下载模型** — ~3.5GB，需提前下载
3. **转写耗时** — 1 小时会议预计转写 3-5 分钟（M4 16GB）
4. **同时只能录一个会议** — 用 `_transcribe_state` 互斥
5. **bot.py 重启会丢失录音状态** — 可接受，录音进程也会随之终止
